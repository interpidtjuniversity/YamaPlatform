## 实现目标

新增一个独立的视频对话模块，提供两个登录用户接口：

1. `GET /grade_feedback/api/video/conversations`
   - 从 `UserHolder` 获取当前登录用户，不能由前端传 userId。
   - 返回该用户全部单轮对话记录，按创建时间倒序。
   - 每条记录包括：`id`、`userPrompt`、`scriptName`、`code`、`videoUrl`、`status`、`errorCode`、`errorMessage`、`createdAt`、`updatedAt`、`finishedAt`。

2. `POST /grade_feedback/api/video/conversations/generate`
   - JSON 请求体：
     ```json
     {
       "prompt": "本轮用户输入",
       "historyLimit": 10
     }
     ```
   - `historyLimit` 默认 10，并设置合理上限，防止一次加载过多历史。
   - 先原子占用当前用户的“生成槽位”；若该用户已有 `SUBMITTING/QUEUED/GENERATING/RENDERING` 任务，直接返回失败及“请等待当前视频生成完毕”。
   - 查询该用户最近 N 条已完成且有代码的记录，转换为：
     ```json
     [
       {"role":"user","content":"历史 user_prompt"},
       {"role":"assistant","content":"历史 code"}
     ]
     ```
   - 调用：
     ```http
     POST http://47.108.214.199:5000/generate_video
     Content-Type: application/json

     {
       "user_prompt":"本轮 prompt",
       "history_messages":[...]
     }
     ```
   - 保存返回的 `script_name` 和 `queued` 状态，并立即返回当前任务记录；不阻塞等待代码或视频生成。

## PostgreSQL 表

采用“一条记录表示一轮对话/一个视频任务”的单表设计：

```sql
create table video_conversation_records (
    id            bigint generated always as identity primary key,
    user_id       varchar(64)  not null,
    user_prompt   text         not null,
    script_name   varchar(255),
    status        varchar(32)  not null,
    code          text,
    video_url     text,
    error_code    varchar(128),
    error_message text,
    poll_count    integer      not null default 0,
    next_poll_at  timestamptz,
    lease_token   varchar(64),
    lease_until   timestamptz,
    created_at    timestamptz  not null default now(),
    updated_at    timestamptz  not null default now(),
    finished_at   timestamptz
);

create unique index uk_video_conversation_script_name
    on video_conversation_records(script_name)
    where script_name is not null;

-- 数据库层保证同一个用户最多只有一个正在执行的任务
create unique index uk_video_conversation_user_active
    on video_conversation_records(user_id)
    where status in ('SUBMITTING', 'QUEUED', 'GENERATING', 'RENDERING');

create index idx_video_conversation_user_created
    on video_conversation_records(user_id, created_at desc);

create index idx_video_conversation_poll_due
    on video_conversation_records(next_poll_at)
    where status in ('QUEUED', 'GENERATING', 'RENDERING');
```

状态在本系统中统一规范成大写：
- `SUBMITTING`：已占位，正在调用生成接口
- `QUEUED`
- `GENERATING`
- `RENDERING`
- `COMPLETED`
- `FAILED`

## 代码结构

### 1. 配置与 HTTP 客户端

- 在 `application.yml` 增加：
  - `video-generation.base-url`，默认 `http://47.108.214.199:5000`
  - 连接/读取超时
  - 状态轮询间隔、租约时间、每次领取数量
- 新增带明确 connect/read timeout 的专用 `RestTemplate` Bean。
- 新增 `VideoGenerationClient`，负责：
  - `generateVideo(prompt, historyMessages)`
  - `getStatus(scriptName)`，按已确认的默认契约调用 `GET /get_status?script_name=...`
  - `getCode(scriptName)`
- 所有 query 参数通过 `UriComponentsBuilder` 编码，不直接拼接 `script_name`。
- 明确区分 200、202、404、500 和网络错误，不把所有错误静默转换成 null。
- 后端不会轮询或下载 `/get_video`；只在完成后构造视频 URL：
  `http://47.108.214.199:5000/get_video?script_name={编码后的scriptName}`。

### 2. 实体、请求/返回模型和 DAO

新增：
- `VideoConversationRecord`：映射 PostgreSQL 表。
- `VideoConversationRequest`：`prompt`、`historyLimit`。
- `VideoConversationModel`：前端返回模型。
- `VideoHistoryMessage`：`role/content` 上游消息模型。
- `VideoConversationDao`，使用现有 `pgJdbcTemplate`：
  - 原子插入 `SUBMITTING` 记录；部分唯一索引冲突表示已有运行任务。
  - 查询当前用户所有记录。
  - 查询最近 N 条 `COMPLETED` 且 `code is not null` 的历史，并调整为时间正序发送给上游。
  - 保存 `script_name` 与 `QUEUED`。
  - 原子领取到期轮询任务，写入 `lease_token/lease_until`，支持应用重启及多实例恢复。
  - 使用租约令牌条件更新状态，避免旧 worker 覆盖新状态。
  - 完成时原子保存 `code/video_url/COMPLETED`；失败时保存错误详情。

### 3. Service 层业务

新增 `VideoConversationService` 和实现类，Controller 只负责参数接收、读取登录用户和包装 `ResultModel`：
- 校验 prompt 非空及长度。
- 先插入 `SUBMITTING`，依靠 PostgreSQL 部分唯一索引解决并发重复提交，而不是“先查再插”。
- 插入冲突时读取当前活动任务，返回“请等待当前视频生成完毕”。
- 组装最近 N 轮历史，调用 `generate_video`。
- 成功后更新为 `QUEUED`；调用异常则将占位记录改为 `FAILED`，避免用户永久无法继续提交。
- 历史接口只查询当前登录用户的数据。

### 4. 后台任务状态管理

新增短周期 `@Scheduled` 状态扫描器：
- 定时方法只从 PostgreSQL 原子领取一小批到期任务，并投递到独立有界线程池，不在 Spring 默认单线程 scheduler 中直接执行阻塞 HTTP，避免影响现有 `GroupExamAutoSubmitter`。
- 通过数据库租约支持进程重启和多实例，不只依赖 JVM 内存状态。
- 调用默认状态接口：
  `GET /get_status?script_name=...`
- 状态处理：
  - `queued/generating/rendering`：更新相应内部状态和下一次轮询时间。
  - `completed`：调用 `/get_code`；200 时保存代码、构造视频 URL并标记 `COMPLETED`。若代码接口暂时返回 202，则延后再轮询。
  - `failed`：保存 `error_code/error` 并标记 `FAILED`。
  - 404：标记 `FAILED`，错误为 `Video job not found`。
  - 临时网络错误：释放租约并延后重试；设置最大连续失败次数/最长任务时限，超过后标记 `FAILED`，避免永久运行。
- 线程池在 `@PreDestroy` 中关闭。

### 5. Controller 与响应

新增 `VideoConversationController`，不把业务和数据库代码写进 Controller：
- `GET /grade_feedback/api/video/conversations`
- `POST /grade_feedback/api/video/conversations/generate`
- 使用 `UserHolder.getValue().getStudentId()` 作为唯一用户身份。
- POST 接口增加现有 `@Limit` 限流。
- 提交成功返回任务记录（一般为 `QUEUED`）；存在活动任务时返回 `success=false`、提示“请等待当前视频生成完毕”，并可在 `data` 中附带该活动任务供前端展示。

## 验证

- 编译整个项目。
- 增加针对状态解析与业务状态流转的测试，覆盖：
  - 正常 queued 提交；
  - 同一用户并发提交只允许一个；
  - 202 处理中；
  - completed 后获取 code 并生成 videoUrl；
  - 404/failed；
  - 网络异常后延迟重试；
  - 历史消息严格按 `user/assistant role/content` 和时间正序发送。

说明：由于上游当前没有提交幂等键，在极端情况下，若上游已经接收任务但本应用在保存 `script_name` 前崩溃，无法从上游反查该任务。这一窗口无法仅由本地数据库完全消除；实现会通过 `SUBMITTING` 占位、超时失败恢复和错误记录将影响控制到最小。
